# 拡張機能の画面テスト

Claude、Codexなどで共通の手順を使う。画面操作のAPIは、その実行環境で利用できるcomputer-useの説明に従う。ツールが存在しない場合、存在するように扱わない。

## 起動

リポジトリのルートでシェルから実行する。画面経由で端末を操作しない。

```powershell
npm.cmd run compile
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/start-ui-test.ps1
```

起動スクリプトはインストール済みVS Codeで現在の`dist/`を開く。通常のVS Codeとは別のユーザーデータ・拡張機能フォルダーを使う。毎回`test-results/manual-ui/<日時>/workspace/sample/`にサンプルをコピーする。編集や保存はコピーで行う。元のサンプルを書き換えない。既存テストウィンドウを勝手に閉じない。

起動せず準備だけ行うときは`-PrepareOnly`。`code.cmd`が見つからない環境では`-CodeExe <インストール済みCode.exeのパス>`を渡す。起動条件は各実行フォルダーの`launch.json`に残る。

## 画面操作

1. computer-useのスキルと必須の操作説明を読む。CodexのWindowsプラグインでは`node_repl`から`@oai/sky`を初期化する。他の環境では提供された公式ツールを使う。
2. アプリ一覧から実際に返されたVS Codeウィンドウを選ぶ。`MDLP UI Test`やExtension Development Hostを目印にする。候補が複数ならウィンドウ内容を見て特定する。IDや座標を推測しない。
3. スクリーンショットを見て、sampleがライブプレビューで開いていることを確認する。通常の文字編集画面なら「Reopen Editor With…」からMarkdown Live Previewを選ぶ。
4. 観察、1操作、再観察を繰り返す。フォーカスを確認してから入力する。スクリーンショットや要素番号は画面変更後に再取得する。
5. 信頼・認証・セキュリティの画面が出たら、環境のルールに従いユーザーに引き継ぐ。未確認のままテストを通過扱いにしない。

## 確認範囲

sampleの冒頭「確認のしかた」を基準に、変更に関係するものを操作する。全体確認を頼まれた場合は、以下を確認する。

- 差分：`+`は緑、`-`は赤、`@@`は青。`+++`/`---`は太字。普通のコードや変更なしの行には差分の色が付かない。明るいテーマと暗いテーマで読める。
- 表：セルを編集、Tab移動、Enter確定、Esc取り消し。行・列を追加し、元の記法へ切り替えて戻す。
- Mermaid・draw.io：描画、ソースへの切り替え、表示へ戻る、拡大・縮小・リセット。
- 先頭のYAML：表示とソースを切り替える。カーソル移動だけで勝手に切り替わらない。
- Ctrl+F検索、次の一致、置換、Esc。Ctrl+Dの複数選択。Ctrl+B/Ctrl+Iと取り消し。
- ローカル画像と別サンプルへのリンク。画像貼り付けはクリップボードにテスト画像がある場合のみ実施し、ない場合は未確認とする。
- Outline移動、タイトルバーの切り替え、CSS Themesの反映。再起動時の状態保持は専用テストウィンドウで確認する。

## 証拠と中断

実行フォルダーに`result.md`を作り、確認項目・実際の結果・成功/失敗/未確認・ビルド日時・使ったウィンドウ名を記録する。スクリーンショットはツールが保存機能を提供する場合だけ保存する。操作できたことと目で表示を確認したことを分ける。

初期化に失敗した場合は、ツールの回復手順に従い再試行を限定する。例：`failed to write kernel assets`は画面操作前の実行環境の不具合。セッションリセット後も続くなら、古い座標で操作せず正確なエラーを記録する。自作のUI操作用プログラムで迂回しない。

自動テストは[共通testスキル](../test/SKILL.md)で補完できる。ただしブラウザー内のテストが成功しても、実際のVS Codeをcomputer-useで確認済みとは報告しない。
